## 3. 本番接続エラー（★解決済み・要フォロー）

**事象**：本番（実API）実行が「Connection error」で全問失敗していた（`20260716_111641`）。

**原因（特定済み）**：`diag_connection.py` の結果より
`[SSL: CERTIFICATE_VERIFY_FAILED] unable to get local issuer certificate`。
Mayaさんのマシンは社内CA/中間証明書が **Windowsの証明書ストア**にはあるが、
httpx が使う **certifi** には無いため検証失敗。`urllib` は Windows ストアを使うので 401（成功）、
`httpx`（Claude SDK）は certifi のみ参照で失敗、という差が出ていた。プロキシは無関係。

**対応（実装済み）**：`truststore` を導入し、Pythonに **OSの証明書ストア**を使わせる。
- `src/llm_client.py` の先頭で `truststore.inject_into_ssl()` を実行（未導入なら無視）。
- `src/diag_connection.py` も同様。`requirements.txt` に `truststore>=0.9.0` 追加。
- 検証：ダミーキーで anthropic 呼び出し → 以前のSSLエラーが消え `AuthenticationError(401)` に変化。
  ＝ TLS到達成功。本物キーなら成功する。

**残タスク（ユーザーPCで実施）**：
1. `pip install truststore`（または `pip install -r requirements.txt`）。
2. `python src\diag_connection.py` → [1]`truststore: 有効`、[4]「成功」を確認。
3. `monitoring_gui.bat` で本番を1回実行し、実データ取得を確認（`data_reset.bat`後が望ましい）。

> 補足：Cowork（アシスタント側サンドボックス）もMITM型SSLプロキシのため同種のSSLエラーが出るが、
> これはユーザーPCの問題とは別。実APIの最終確認はユーザーPCで行う。

  「コードはBOX配布→各自ローカルにコピーして実行」を推奨。
- 全員分の結果集約が必要なら「実行は1台/スケジュールに集約、他は閲覧のみ」構成も検討可。

## 8. ローカルGitでの作業フロー ★v8

**前提**：プロジェクトはローカルGitリポジトリで管理（作業環境の正＝`Documents/GitHub/GEO`、リモート＝`github.com/MayaNakajima/GEO`）。機密（`.env`）と生成データ（`data/` の results/logs/reports・dashboard.html）は `.gitignore` で除外済み。

**原則**：`main` ブランチには直接コミットしない。**作業ごとにブランチを切って作業・コミットし、動作確認がOKになったら `main` へマージコミット（`--no-ff`）する。**

### 8-1. フロー（コマンド）

```bash
# 0) リポジトリへ移動（初回のみ clone）
cd C:\Users\612316\Documents\GitHub\GEO
# git clone https://github.com/MayaNakajima/GEO.git  ← 初回・別PCのみ

# 1) 最新の main を取得
git checkout main
git pull origin main

# 2) 作業用ブランチを作成（命名例：feature/dashboard-〇〇、fix/ssl-〇〇、docs/〇〇）
git checkout -b feature/作業名

# 3) 変更 → こまめにコミット（このブランチ上で何回でも）
#    コミットメッセージは §8-3 の規約に沿って書く
git add -A
git commit -m "feat: 変更内容の要約"   # 本文も書くなら git commit（エディタ）

# 4) 動作確認（§8-2）。OKになるまで 3) を繰り返す。

# 5) 確認OK → main へマージコミット（マージ履歴を必ず残す）
git checkout main
git pull origin main
git merge --no-ff feature/作業名 -m "Merge: 作業名"

# 6) リモートへ反映（プッシュ）
git push origin main

# 7) 不要になった作業ブランチを削除
git branch -d feature/作業名
# リモートにも上げていた場合： git push origin --delete feature/作業名
```

- **`--no-ff`（no fast-forward）** を付ける理由：作業をひとまとまりのマージコミットとして履歴に残すため。問題が起きたときにマージ単位で戻せる（`git revert -m 1 <マージコミット>`）。
- ブランチ命名の目安：新機能=`feature/`、不具合修正=`fix/`、ドキュメント=`docs/`、実験=`spike/`。

### 8-2. マージ前チェック（確認OKの基準）

- **機密・生成データが追跡されていないこと**：`git status` で `.env` と `data/` の生成物が **Untracked/Ignored** であることを確認（誤って `git add` していないか）。
- **ダッシュボードが生成できること**：`python -c "import sys;sys.path.insert(0,'monitoring/src');from pathlib import Path;import dashboard;dashboard.render(Path('monitoring/data/reports'),Path('monitoring/data/dashboard.html'))"` が通り、`dashboard.html` をブラウザで開いて表示崩れがない。
- **ドライランが通ること**：`cd monitoring && python src/runner.py --dry-run --all`（API課金なし）。
- 変更内容がコミットメッセージと一致していること（`git diff main...feature/作業名` で差分確認）。

### 8-3. コミットメッセージの規約（作業内容をブランチに残す）

**作業内容はコミットメッセージに残す。** 各コミットは「何を・なぜ・どう確認したか」が後から追える形で書く。ブランチ上のコミット群がそのまま作業記録になる。

**書式**：

```
<種別>: <要約（日本語可・50字目安・末尾に句点は付けない）>
                       ← 1行空ける
- What : 変更した内容（箇条書き）
- Why  : なぜ変更したか／背景・課題
- 確認 : どう動作確認したか（ドライラン／ダッシュボード表示 等）
```

**種別プレフィックス**：

| 種別 | 用途 |
|---|---|
| `feat` | 新機能 |
| `fix` | 不具合修正 |
| `docs` | ドキュメント |
| `refactor` | 挙動を変えないコード整理 |
| `test` | テスト追加・修正 |
| `chore` | 設定・雑務（`.gitignore`・依存更新 等） |

**例**：

```
feat: ダッシュボードにSet比較・崖の分析タブを追加

- What : dashboard.py に3つ目のタブを追加。特異度カーブ(D1→D4)・崖の赤強調・
         Set1平均の点線基準・解釈文・次アクション・Set1×Set2サマリー表。
- Why  : 「どの具体度から当社が消えるか(崖)」を画面で読めるようにするため。
- 確認 : trend/timing JSON で render 実行しブラウザ表示OK。崖=D1→D2 を確認。
```

**運用メモ**：

- こまめにコミットしてよいが、**1コミット＝1つの意味のまとまり**にする（無関係な変更を混ぜない）。
- 短い変更は1行だけ（`fix: 崖判定のしきい値を10%に統一`）でも可。本文は必要なときに書く。
- **マージコミット**（§8-1 手順5）には、そのブランチの作業要約を1〜3行で書く（例：`Merge: Set比較タブ追加（崖の可視化）`）。→ ブランチ単位の作業内容も履歴に残る。
- 複数行メッセージは、`git commit`（エディタが開く）で書くか、`-m` を複数指定（`git commit -m "件名" -m "本文"`）する。

### 8-4. 1人運用でもブランチを使う理由

作業単位が履歴に残って後から追える／確認前の未完成状態を `main` に混ぜない／問題時にブランチやマージ単位で安全に戻せる。**「mainは常に動く状態」を保つ**のが目的。
