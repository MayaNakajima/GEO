## 背景（別アプリで判明した事実）
姉妹アプリ `GEO-analysis`（回答全文の深掘り・突合）で回答本文のコンテキスト分析を実装したところ、
**`mention_detected=True`（ヒット）の一部が誤検知（false-positive）** であることが分かりました。
具体的には、Raffiria／ラフィーリア に関する設問で、AIが「その名称は把握していない／確認できる情報を
持ち合わせていない」と**留保・拒否しているのに、設問由来のブランド名を復唱したためヒット判定**されています。

実データ（`data/results/results_20260727_170500_r1.csv` ほか）での具体例：
- `Q-C3EC-A6-B7b-042`「Raffiriaとはどのようなブランドですか？」
  → 回答「『Raffiria』について確認いたしましたが、私の知識の範囲では…確実な情報を持ち合わせておりません」= **本来はミス**
- `Q-S2-C3-D1-02`「ラフィーリア（Raffiria）はどんな医療機関に導入されていますか？」
  → 回答「…確認できる資料の中に見つけることができませんでした」= **本来はミス**
- （対照・維持すべき真陽性）`Q-C5-A6-B8-053`「オンワードコーポレートデザインはどのような会社ですか？」
  → 会社説明を実際に生成 = **これは正しくヒット。修正後も True のままであること**

## 根本原因（`src/detector.py`）
1. `entities = [kw for kw in self.all_keywords if kw.lower() in lower]`（57行目）が
   **回答本文のどこかに部分一致すれば検出**とする。文脈（肯定/否定）を見ていない。
2. `config/detection_keywords.json` の `secondary`（`Raffiria` / `ラフィーリア` / `オンワードCD`）は
   **設問文にそのまま含まれるブランド名**。AIが設問を復唱・引用するだけで一致してしまう。
3. とくに指名質問（Set2 の D1 や C3-EC のブランド設問）は設問自体に自社名を含むため、
   「設問エコー」と「AIが実際に自社を認識・説明した」ことの区別が必須。

## 修正ゴール / 受け入れ基準
- 上記の Raffiria/ラフィーリア 留保・拒否回答が **`detected=False`** になること。
- 会社説明を実際に生成している回答（例 `Q-C5-A6-B8-053`）は **`detected=True` のまま**（真陽性を壊さない）。
- 判定は **オフライン・決定論的**（現状同様、外部API不要）を維持。
- 誤検知の判断根拠を追えるよう、結果に補助情報（例 `disclaimer_detected` フラグ／理由）を残す。

## 推奨アプローチ（A を主軸に。B/C は補強、D は将来）
**A. 否定・留保ガード（推奨・最小変更）**
　キーワードがヒットした箇所の**同一文（前後の文境界 `。！？改行` まで）に留保・否定フレーズが共起する場合は
　検出を無効化**する。留保フレーズ例（要調整）：
　「持ち合わせておりません／見当たりません／存じ上げません／確認できません／確認できる…ありません／
　見つけることができませんでした／わかりません／特定できません／該当する（企業|ブランド|情報）…（ない|ありません）／
　私の知識の（範囲では|中には）／情報がありません／申し訳（ございません|ありません）」。
　→ ヒット文が留保文なら `detected=False`（または `entities` から除外して再評価）。`disclaimer_detected=True` を返す。

**B. 設問エコーの除去（Aと併用推奨）**
　`detect(text, domain, question=...)` に**設問文を渡し**、回答から設問の引用部分（設問と重複する語・「『…』について」等の
　復唱）を除外してから照合する。少なくとも「設問にしか無いブランド名の単独一致」は根拠として弱いものとして扱う。

**C. 指名質問(D1)の扱い**
　D1/ブランド指名設問では `secondary` の**単独一致だけでは検出としない**（`primary` の肯定的言及、URL一致、
　または会社説明の実体が必要）等、ティア別に閾値を上げる案。過剰検出が続く場合の追加策。

**D. 将来：LLM/分類器による判定**
　「回答は自社を実在として説明・推薦したか、留保・否定したか」を判定する軽量分類。堅牢だがコスト・ネット依存が増えるため、
　A/B で不足する場合の将来オプション。

## 実装ポインタ
- 変更の中心は `src/detector.py` の `detect()`（キーワード一致の後段に留保判定を追加）。
- 呼び出しは `src/runner.py:225`（`detector.detect(answer, domain=question["axis_domain"])`）。
  B案を採るなら **`question=question["question"]` を渡すよう `detect()` の引数と呼び出しを拡張**。
- CSV/JSONへの新フィールド（`disclaimer_detected` 等）を追加する場合は `runner.py` の結果 dict と
  出力側（`logger.py` / `reporter.py`）の列定義も更新。**既存列は削らず追加のみ**（姉妹アプリ GEO-analysis は
  同じCSVを疎結合で読むため、`mention_detected` 等の既存スキーマは互換維持すること）。

## 回帰チェック（必須）
- 上記3例（誤検知2件＝False化／真陽性1件＝True維持）を最小の検証スクリプトかドライランで確認する
  （テストディレクトリは未整備なので、`src/` に簡易チェックを置くか、`diag_connection.py` に倣った確認手順でも可）。

## 既存データの扱い
- 判定はCSV書き込み時に確定するため、**過去のCSVは再判定されない**。修正後は
  (a) 今後の測定から正しくなる、(b) 過去分を直すなら保存済み `answer` を使った**再判定バッチ**が必要、の2択。
  どちらにするか（過去分の遡及是非）を実装前に確認・記録すること。
